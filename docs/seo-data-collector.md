# Локальный сборщик SEO-данных

Этот инструмент только читает данные и сохраняет их на компьютере владельца.
Он не меняет сайт, счётчики, цели, данные в поисковых системах или настройки
индексации. Расписание намеренно не добавлено.

## Что собирается

Сначала в отчёте всегда идёт Яндекс.

- Яндекс Вебмастер: показы, клики и позиции, популярные запросы, данные по
  устройствам, ИКС, страницы в поиске, индексация, диагностика, примеры битых
  внутренних и внешних ссылок.
- Яндекс Метрика: поисковые визиты и пользователи, отказы, глубина и время
  визита, поисковики, устройства, посадочные страницы и достижения всех
  доступных целей.
- Google Search Console: показы, клики, CTR и позиция по датам, запросам,
  страницам, устройствам и странам.
- Google Analytics 4: Organic Search — сессии, активные и новые пользователи,
  вовлечённые сессии, engagement rate, рассчитанное среднее время вовлечения,
  источники, устройства, посадочные страницы и key events.

Для каждого периода также собирается предыдущий период такой же длины. Если
поисковая система ещё не завершила последний день, инструмент сдвигает
фактическую границу периода к последнему полному дню и заново рассчитывает
равный предыдущий период. В отчёте остаются запрошенные и фактические даты,
а также причина сдвига.

Основной коммерческий кластер находится в
`scripts/seo/config/commercial-query-cluster.json`; порядок слов и основные
грамматические формы учитываются. Отдельно и по фиксированным правилам
показываются соседние коммерческие запросы, бренды/конкуренты, географические
или офлайн-запросы, информационные запросы и прочие запросы. Только основной
кластер попадает в основную коммерческую сводку.

## Локальные настройки

В `.env.local` нужны идентификаторы:

```dotenv
GOOGLE_SEARCH_CONSOLE_PROPERTY=sc-domain:chinachild.ru
GA4_PROPERTY_ID=338734549
YANDEX_OAUTH_TOKEN=
YANDEX_METRIKA_COUNTER_ID=
YANDEX_WEBMASTER_HOST_ID=
```

Google использует существующие Application Default Credentials (ADC) из
`~/.config/gcloud/application_default_credentials.json`. Сервисный аккаунт и
его JSON-ключ не нужны. Файл ADC, OAuth client JSON, access token и refresh
token нельзя копировать в репозиторий.

`YANDEX_OAUTH_TOKEN` — секретный локальный OAuth-токен только с правами
`metrika:read` и чтения Яндекс Вебмастера. Токен передаётся только в заголовке
`Authorization`; команда его не печатает и не добавляет в URL.

Идентификаторы счётчика и хоста необязательны, если найден ровно один ресурс
`chinachild.ru`. При нескольких подходящих ресурсах инструмент ничего не
угадывает: он выводит кандидатов и просит указать ID.

## Команды

```bash
npm run seo:check
npm run seo:collect -- --days=90
npm run seo:collect -- --start=2026-04-01 --end=2026-06-30
npm run seo:report
```

`seo:check` проверяет ADC и доступ к обеим Google properties, затем токен,
счётчики, цели, пользователя и хосты Яндекса. Для Вебмастера команда также
делает короткие чтения сводки сайта и истории запросов: токен иногда позволяет
увидеть хосты, но приложение OAuth не имеет доступа ко всем нужным read-only
методам. В таком случае команда покажет точный отказ API и завершится с
ошибкой. Отсутствующий Яндекс-токен не мешает проверке Google, но также даёт
ненулевой код конфигурации.

`seo:collect` по умолчанию заканчивает период вчерашним днём, делает
ограниченные повторы при rate limit и временных сбоях, обрабатывает страницы
ответов и записывает частичный запуск даже при ошибке одного источника. Такой
запуск возвращает ненулевой код, чтобы ошибка не выглядела успехом.

`seo:report` берёт последний запуск. Для конкретного запуска:

```bash
npm run seo:report -- --run=2026-07-30T10-20-30-000Z
```

## Где лежат результаты

Вся папка `seo-data/` игнорируется Git:

```text
seo-data/
  latest.json
  runs/<run-id>/raw/
  runs/<run-id>/normalized/
  reports/<run-id>/seo-report.json
  reports/<run-id>/summary.md
  reports/<run-id>/csv/
```

Raw JSON нужен для проверки исходного ответа. Normalized JSON сохраняет
поставщика, поисковик, период, тип агрегации и исходное значение метрики. CSV
удобны для таблиц, а `summary.md` — короткий отчёт для владельца. В частности,
`search-opportunities.csv` содержит полный список запросов около первой
страницы и со слабым CTR, `broken-internal-links.csv` — доступные примеры
источников и целей битых ссылок, а `lead-configuration-review.csv` — все цели
Метрики и настроенные key events GA4 за оба периода, включая нулевые значения.
Markdown показывает только первые 50 возможностей и всегда указывает полное
число строк.

Итоговый Markdown разделён по смыслу:

1. поисковая видимость — Яндекс Вебмастер и Google Search Console;
2. органический трафик — отдельно Яндекс Метрика и GA4;
3. конверсии — отдельно цели Метрики и key events GA4.

Метрика и GA4 показывают собственные общие итоги органического трафика. Когда
доступны измерения поисковой системы или источника, внутри каждой системы
отдельно показываются Яндекс, Google и остальные источники. Визиты/сессии не
сравниваются напрямую с кликами поисковых кабинетов.

При пересечении отчётного периода с приблизительной датой запуска/миграции
`2026-06-01` отчёт предупреждает, что дата не подтверждена, а рост включает
эффект запуска/миграции и не является чистым SEO-ростом.

## Как понимать различия

- Визит Метрики не равен сессии GA4.
- Пользователь Метрики не равен active user GA4.
- Позиции Яндекса и Google рассчитываются по разным методикам.
- Уникальных пользователей нельзя складывать по дням, устройствам,
  поисковикам или страницам. Отчёт использует отдельные итоговые строки API.
- Данные разных поставщиков показываются рядом, но не суммируются.
- Цель или key event не считается лидом автоматически. Таблица проверки
  конфигурации намеренно не выбирает «главную» конверсию: владелец должен
  подтвердить, какие названия в кабинетах действительно означают лид.

Search Console может скрывать анонимные запросы и отдаёт не гарантированно
полный список строк. Вебмастер отдаёт ограниченный топ популярных запросов:
инструмент получает до 500 по показам и до 500 по кликам и удаляет дубли.
Поэтому отчёт отдельно показывает общие клики/показы поставщика, сумму
доступных строк запросов и процент покрытия; классификация применяется только
к доступным строкам. Суффикс цели вида `@dzen.ru/...` в ответе Вебмастера
сохраняется как метаданные цели, а не как часть поискового запроса.
Метрика может применять семплирование и скрывать чувствительные данные малых
аудиторий. GA4 может применять thresholding и строку `(other)`. Эти признаки и
фактические диапазоны сохраняются в metadata.

Метод битых внутренних ссылок Вебмастера возвращает примеры, а не
гарантированно полный перечень. Отчёт различает число строк примеров и число
уникальных целей, показывает источник → цель и отдельно сообщает доступный
статус/причину из истории.

## Ошибки и замена доступа

Сообщения различают отсутствующую переменную, неверный ID, неоднозначный
ресурс, отказ в доступе, rate limit и временный сбой. Секреты редактируются из
ошибок. Пустой основной набор данных не считается успешным сбором.

Чтобы заменить Google ADC, сначала отозвать локальные credentials командой
`gcloud auth application-default revoke`, затем снова выполнить авторизацию
ADC с read-only scopes Search Console и Analytics. Чтобы заменить Яндекс
доступ, отозвать токен/доступ приложения в настройках Yandex ID, выпустить
новый read-only токен и заменить только значение `YANDEX_OAUTH_TOKEN` в
`.env.local`.

Никогда не отправляйте содержимое `.env.local`, ADC или OAuth-токены в чат,
задачу, commit или отчёт.
